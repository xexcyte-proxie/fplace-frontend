# Positioning audit and diagnostic protocol

## Audit before instrumentation (2026-10-27)

This checkout is a TypeScript/Vite PWA with a plain JavaScript AR iframe. No Flutter application is present. Existing uncommitted simulation and phone-report work is preserved.

Pipeline and authorities:

1. `services/location-service.ts` handles location acquisition/presence. `position/providers/gpsProvider.ts` independently watches navigation GPS and re-emits the last geographic fix on orientation events, preserving its GPS timestamp. `position/positionProvider.ts` uses generation guards and stops an existing subscription on restart. Mappedin BlueDot has its own sensor path in `map/markers.ts`; simulator-parallel mode disables that sensor authority during provider navigation. Presence GPS and navigation GPS are distinct subscriptions, not automatically duplicates.
2. `MapApp.initializeVenueGpsReference` creates a reference per venue. `VenueGpsReference.capture` and `.anchor` use nullish assignment: subsequent GPS callbacks and route selections cannot overwrite either point on that object. Map anchor is the first route origin, not necessarily the venue centroid. New objects are allocated on venue unload/change and explicit development preference changes. Async initial fixes check reference identity. Thus write-once semantics are supported by code, but object replacement needs a timeline.
3. `VenueGpsReference.translate` converts physical displacement to local metres and then geographic coordinates around the fixed map anchor. `handleProviderFrame` applies this once; AR receives projected map coordinates rather than applying the development transform again. Actual physical coordinates go to presence publishing.
4. `MapApp.projectFrameOntoRoute` calls `coordinateTransformationService.snapToRoute` with floor, leg and previous progress. `snap-along-continuity.ts` constrains segment selection. Raw fix acceptance requires finite coordinates, age <=15 s, accuracy <=30 m; route snap acceptance requires off-route <=30 m. These bounds do not establish that displacement is physical movement.
5. `syncLiveRouteProgress` is the 2D progress authority. It applies `AlongPathProgressStabilizer`, then `advanceContinuousAlongMeters`, taking the greater value. That second path can advance toward a noisy forward snap despite a stabilizer hold: a candidate for stationary drift, not a proven device cause. Display position can remain at the raw snap when continuous, or bind to stabilized progress otherwise. `map/markers.ts` has an additional stationary filter for its native GPS path; it is not the authority for provider progress. Map camera follow/recentering changes camera, not the provider's coordinates.
6. `getNavigationProgressSnapshot`, `syncNavigationToAr`, animated BlueDot callbacks and `dispatchPositionToAr` feed AR. Parent navigation sync uses source `pwa`; bridge payloads can assign accuracy 4 independently of original GPS accuracy. The report must retain original GPS accuracy separately.
7. `RouteNavigator.applyNavigationSync`, `applyPosition`, `applySimulatorPosition`, `syncSimulatorProgressFromAuthority`, `advanceAlongPath`, `getDisplayAlongPathMeters`, and parent simulator display ticks can update AR progress/maneuvers. Display progress can blend/extrapolate GPS or use `slam-pose-bridge.js`. SLAM predicts progress by projecting camera X/Z translation onto route direction. Orientation alone is not explicitly added to translation, but SDK translation drift during rotation and alignment changes need measurement.
8. Arrival has independent authorities. PWA `syncLiveRouteProgress` uses `hasArrivedAtDestination`: end tolerance 0.75 m, off-route <=4 m, minimum traveled distance, GPS accuracy <=10 m. AR `applyArrivalLatch` accepts <=5 m, or forceComplete, and does not apply those PWA accuracy/off-route checks. Calls originate in navigation sync, simulator synchronization and maneuver advancement. `lockArrived` posts `fplaces_ar_arrived`; parent `lockNavigationArrival` permanently sets completion and remaining=0. A short route can satisfy AR's generic latch without physical travel. This is source-supported early-arrival risk; only a captured evaluation can identify the branch on the affected phone. No thresholds are changed by diagnostics.
9. `visual-route-state.js` chooses authoritative, display, then snapped progress. `world-route-scene.js` selects a floor/leg section and rebuilds on route/section/anchor revision. `pathGeometry.js` projects into world space. `incremental-ar-path.js` reconciles stable along-route slots, with a 180 ms membership gate; overlapping slots retain instance identity and refresh transforms. `incremental-path-spawn.js` determines spacing, visible maximum and forward horizon. New slots should appear as selected progress advances. Arrival invalidates the route visuals.
10. World-space chevrons have physical dimensions and scale. Perspective projection normally increases apparent size as camera-space depth decreases; this is different from changing physical scale. `applyFadeIn` also fades/hides arrows near/behind the camera using depth (default minimum 0.8 m, fade 0.6 m), so apparent growth can end in disappearance. Camera rotation can change depth/frustum visibility without walking. Capture world transform, depth, scale, opacity and lifecycle together.

## Instrumentation plan

Use one development-owned recorder shared by same-origin PWA and AR, with ordered sequence IDs, wall and monotonic timestamps, bounded events, dropped counts, typed state snapshots and explicit source labels. Record raw sensor callbacks before quality checks, simulation references, accepted/snap/display positions, every arrival latch evaluation and its calling subsystem, parent arrival receipt, AR synchronization, tracking, anchor revisions and sampled arrow transforms. Never call progress-mutating getters solely to take diagnostics.

Provide Start/Stop/Clear/Snapshot/Copy/JSON, default coordinate redaction and optional local offsets. Keep telemetry local. A development stationary switch holds the last accepted navigation frame while raw GPS and camera continue; prevent test-frame presence publishing. A separate scene-root marker stays at one captured world transform across route reconciliation and anchor changes. Warnings report observations with configurable thresholds, without modifying navigation.

## Device protocol

Record A: stationary GPS for 60 seconds. B: rotate in place, first normally then with Freeze accepted position. C: walk a measured distance and note it in the external test notes. D: remain outside destination and retain the first arrival evaluation and parent latch sequence. E: use a long route and compare stable arrow IDs, camera depth, world transform and new slot creation. F: interrupt/recover tracking with the fixed marker enabled. Start recording before opening the venue so origin initialization is retained. Repeat sessions separately; clear between runs.

Desktop tests cannot certify physical displacement, GPS/SLAM accuracy, iPhone permission/clipboard behavior, or XR8 recovery. No actual-device outcome is claimed.

## Implemented controls and export

Run the Vite **development** application (`npm run dev` from the repository root; use the HTTPS development URL on the phone). `AR Debug` is mounted in the PWA, including above its AR iframe. Production builds do not create a recorder or show these controls. The AR iframe joins the parent recorder only when same-origin access succeeds; standalone/cross-origin AR is deliberately not presented as a complete capture.

1. Open AR Debug before entering the venue, press **Clear**, then **Start**. Close the dialog to navigate normally. Recording starts stopped; refreshing the page loses the in-memory session.
2. Reproduce one scenario. **Freeze accepted position** holds the last accepted provider coordinates; if none exist, the first usable frame becomes the held point. Heading, GPS reception and camera tracking continue. `AR Debug · FROZEN` stays visible while the mode is on. The mode persists until toggled off, independently of recording. Native BlueDot sensor ingestion is also suppressed during this test. Normal presence watchers can still publish real GPS; the frozen provider path does not publish test positions.
3. **Fixed world marker** adds a magenta sphere once, three metres ahead of the camera at activation. It is a scene-root object, independent of route disposal and anchor changes. Its coordinate remains fixed until disabled or the scene detaches. Creation requires an attached XR world. Tracking loss may prevent reliable rendering; logged coordinates remain evidence, not proof of world stability.
4. Press **Snapshot** for an explicit current-state capture, or **Stop** to retain the final recorded state. Stop does not disable the freeze/marker tests. Switch them off when finished.
5. For sharing, choose **Local offsets in metres** to retain geographic displacement without exporting the physical/venue origins, or keep **Redact (default)**. **Include absolute GPS** is an explicit local choice. No report is uploaded. Offset spaces are independently based on first encountered physical and venue coordinates, and are approximate over large areas.
6. On iPhone tap **Copy report**. If Safari rejects the Clipboard API, the UI tries selection-based copying and then leaves the text selected with instructions to touch and hold and choose Copy. **Download JSON** downloads the same complete structured report using a Blob where browser downloads are supported. Clipboard/download behavior still needs a physical Safari check.

The JSON begins with a human-readable `summary`. `eventTimeline` has shared sequence numbers, ISO wall time and monotonic session-relative milliseconds; `cause` links synchronous GPS → provider → progress operations. Development navigation sync carries its causal sequence across postMessage delivery. Render samples include route/anchor/progress identities for correlation; independent asynchronous SDK callbacks cannot be claimed to have a proven GPS cause. `positionSamples`, `progressSamples`, `arrivalEvaluations`, `arTrackingEvents`, `arrowLifecycleEvents` and `diagnosticWarnings` are views of that bounded timeline, not additional unbounded collectors.

Capacity defaults to 6,000 events. Oldest records are evicted; `summaryStatistics.dropped` makes incomplete history explicit. Counts cover the recording even if earlier events are evicted. AR poses and arrow observations are sampled at 200 ms; SDK tracking transitions, raw navigation GPS, progress and arrival evaluations are event-based. Membership lifecycle creates/removes/moves are recorded separately. Retained arrows are represented in samples. SDK fields that are unavailable are null; no SDK positioning-confidence estimate or proprietary coordinate is fabricated. Mappedin's public Coordinate exposes geographic coordinates, floor and vertical offset, not public x/y; local-metre displacement comes from the explicit simulation transform and route geometry.

Diagnostic warning thresholds are mutable through `window.FplacesNavigationDiagnostics.config` in a development console (`stationaryM`, `progressJumpM`, `disagreementM`, `poorAccuracyM`, `rotationRad`, `recreationCount`). They are exported and never control navigation. Visual disagreement compares section-local progress plus the section start with route-global authority. Stationary classification is an observation, not proof of physical stillness.

Additional reset/seed authorities: `applyRoute` and `seedRouteProgressFromUser` initialize route distance and progress; `startRouteMovement`/`resumeRouteNavigation` seed and enable live tracking; `clearRoute` and provider stop/reset paths clear progress. These are visible through store state changes and route/simulation identities. `routeSimulating` is also used for live route tracking, so its name alone is not evidence of a synthetic walk. Native Mappedin progress visualization and animated callbacks are recorded separately from the 2D odometer.

## Verification and limitations

Production `npm run build --prefix mappedin-pwa` passes, including TypeScript and PWA generation (existing large-bundle advisory remains). The full suite after implementation reported **908 passed, 13 failed, 4 skipped**. Ten failures require unreachable live backend/Map services (DNS resolution failed); the other three are outside diagnostics: `ui/api-backed-screens.test.ts`, `ui/page-loaders.test.ts`, and `location/domain/venue-presence.test.ts`. No unrelated screen or development-bypass behavior was changed to make them pass.

Focused coverage includes existing simulation-origin immutability and metre-preserving translation tests, GPS jitter/identical fixes and provider lifecycle tests, route progress/arrival latch/segment continuity tests, AR synchronization/retention/rotation tests, and new recorder/export/privacy/control/frozen-provider/marker/arrival-caller tests. The optional real-Three.js frustum test remains skipped because that runtime dependency is not installed; constructor doubles cover rotation/depth visibility and instance retention. Physical perspective rendering is not certified by doubles.

In-app browser verification could not start: the browser tool reported missing sandbox metadata and the sandbox denied binding the local server port. UI control and Safari clipboard fallback paths were exercised with automated DOM doubles. Scenarios A–F still require an actual phone; this implementation establishes evidence collection and does **not** claim to fix stationary drift, early arrival or AR progression.

Final focused regression command (AR, position, routing progress/latch/continuity, live tracking, frozen-provider integration, location service, and markers): **252 passed, 1 skipped across 28 files**. TypeScript and `git diff --check` also passed.
