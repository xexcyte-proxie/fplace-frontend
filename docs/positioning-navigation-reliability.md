# Positioning and navigation reliability — 2026-10-28

This work builds on the positioning lifecycle and diagnostic changes already in the working tree. Those changes were preserved. The earlier audit in navigation-diagnostics.md describes the pre-fix behavior; this document records the subsequent fixes.

## Sequential changes and causes

1. My Location previously evaluated cached venue distance before requesting a fresh fix. It now acquires and publishes the physical fix first, then evaluates venue presence. Requests completed after map/service/simulation-reference replacement are ignored. Simulation captures the physical reference if necessary, uses the existing write-once venue anchor, and explicitly labels the displayed development position. Real locations identify the selected venue when presence permits it, or show geographic coordinates. Missing anchors retain the explanatory message. Provider navigation does not request an additional native GPS watch. Existing permission/error gates remain in use.
2. The provider positioning path bypassed the stationary filter used by native map positioning. Provider GPS now passes through an uncertainty deadband before route projection, rendering, progress and AR synchronization. The threshold is max(1.5 m, 35% of reported accuracy); materially improved accuracy may re-anchor. Fresh timestamps and heading remain live. The filter survives route/provider restarts and resets when map/source/reference identity changes. Physical presence publishing retains physical GPS coordinates. This is noise suppression, not a guarantee of indoor GPS accuracy or proof of movement.
3. Continuous odometer catch-up could override a stationary hold. Held provider positions now retain published travel distance. 2D arrival additionally requires the accepted position within 4 m of the destination, retaining the existing 0.75 m along-path tolerance, accuracy <=10 m, off-route <=4 m and minimum travel rules. AR's former 5 m early-arrival threshold is now 0.75 m. Parent-synchronized AR waits for explicit parent completion; the parent rejects AR arrival messages unless its own completion is confirmed. Standalone AR requires fresh, accurate destination proximity for an unforced latch. Elapsed time/speed no longer extrapolates live GPS display progress. Explicit simulation retains its separate clock. Camera changes cannot confirm parent arrival.
4. Trail geometry identity is now explicitly the accepted route/section object in both initial generation and refresh. Array allocation/cache changes cannot masquerade as route replacement and reset slot membership. Existing spacing, horizon, count, arrival clearing and endpoint exclusion remain unchanged. A full-route regression sees exactly the 19 valid two-metre grid placements on a 40 m path, never more than eight simultaneously. Existing route replacement, floor/anchor invalidation, hairpin, reverse travel and visual stability tests remain active. Fewer arrows near the destination or on short routes are intentional when no valid placements remain.
5. The copyable navigation reports now include location-button request/fix/center/failure, physical versus simulated coordinates, provider-filter held decisions, accepted progress and parent-confirmation rejection. Existing subscription, transform, blue-dot, arrival and trail records are retained. Follow docs/navigation-diagnostics.md for the debug report controls and capture protocol. Reports include precise location; review them before sharing.

Verify both real geographic positioning and explicitly enabled development venue simulation; simulation with missing map geometry must explain why placement is unavailable.

Confirm that noise does not change travel/arrival, that legitimate walking advances without excessive delay, and that the dot survives start/destination selection and route regeneration. ## Development simulation follow-up verification

The local .env and .env.local enable `VITE_ENABLE_VENUE_GEOLOCATION_SIMULATION=1`. Configuration also requires Vite `DEV`; a production/Netlify build does not activate simulation even when that flag is set. This development-only restriction was preserved.

Simulation is a temporary coordinate transform, not an edit to catalog coordinates: one physical reference per venue opening maps to a loaded venue-map anchor (selected section, exterior entrance, or mapped-space center); later GPS displacement is preserved in signed local metres. Capture and anchor remain write-once through reroutes and My Location. New venue sessions create a new reference; late results from a previous venue are ignored. GPS coordinates published as physical user location remain physical; map/AR positions use the translated coordinate. Stabilization follows translation and does not change either reference point.

The My Location UI no longer disables acquisition because of a cached physical venue-distance result. A further mismatch was fixed in the route sheet: Begin/AR now respect an actually active simulation reference without requiring the unrelated remote-AR environment bypass. Normal real-location venue restrictions remain in effect when simulation is inactive.

Follow-up regression: 86 tests passed across six files, including signed north/south/east/west displacement, frozen input immutability, reroute/reference stability, venue replacement and late callbacks, physical-versus-translated publishing, AR coordinate sharing, My Location, marker lifecycle, and navigation-control availability. TypeScript and diff checks pass. Physical-phone movement and permission behavior remain unverified. The original route-start restriction described in that follow-up has been removed; see [route-independent simulation](route-independent-simulation.md).
